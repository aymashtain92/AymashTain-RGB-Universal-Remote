This is a genuinely fun reverse-engineering project, and the good news is you're not starting blind — the overwhelming majority of cheap unbranded BLE LED strips/bulbs run one of a small handful of known clone chipsets (the "Magic Home / Triones / Happy Lighting" family that tools like flux_led and Home Assistant's own LED integration already talk to). That gives us a real head start instead of pure guesswork.

Before I lay out the plan, a few honest technical realities that shape what this can actually be:

Bluetooth: A browser can talk real BLE via the Web Bluetooth API — scan, connect, read/write GATT characteristics. This works in Chrome/Edge (desktop + Android). It does not work in Safari/iOS at all (Apple blocks it) — if you're on iPhone we'd need a workaround browser like Bluefy, or a native app down the line.
IR: No browser can emit or sniff IR — there's no such web API. So IR support means one of two things: (a) a reference tab documenting the well-known NEC codes these generic 24/44-key remotes use, useful if you later pair it with a cheap ESP32/Broadlink IR bridge, or (b) if you already own such a bridge, the app can send it commands over HTTP/WiFi. It can't be "IR from the laptop's Bluetooth antenna" — that's not physically how IR works.
USB: Many of these controllers' USB dongles are just a USB-serial chip (CH340/CP2102) speaking simple serial commands. I'd use the Web Serial API for that (same Chrome-family restriction, no Safari/Firefox).
Given that, here's the plan:

App: a BLE/Serial LED-protocol lab + custom remote builder
1. Connect — one-tap scan/pair for BLE (and Serial for USB dongles), with the common clone-chip service UUIDs pre-loaded so it tries the "known" protocol automatically first.

2. Quick Control — if it turns out to be one of the known clone protocols (very likely), you get instant working sliders: power, RGB, brightness, built-in effect + speed — no reverse-engineering needed.

3. Reverse-Engineering Lab — for anything that doesn't match a known protocol: a raw hex command sender + a "what did that do?" label field. Every attempt gets logged (bytes + your label + timestamp), with a diff view that highlights which byte changed between two labeled commands — this is how you (or I, if you paste the exported log back into our chat) spot which byte is color, which is speed, etc.

4. Remote Builder — once a command is verified, drag it onto a custom on-screen remote as a named button. Build exactly the remote you actually want, saved locally in your browser.

5. Music-Sync Studio — instead of fighting the device's locked-down mic-based "dancing" mode, the app does its own audio analysis (Web Audio API) on either your mic or a song file/PC audio you feed it directly, does beat/frequency-band detection in-browser, and drives the light's color/brightness commands itself in real time — with a manual latency-offset slider to compensate for Bluetooth's write delay. This replaces the stock app's hidden logic entirely rather than trying to unlock it.

6. IR Reference — documented NEC hex codes for typical 24/44-key remotes, plus an optional field to point at an IR-bridge if you have one.

Data (your command log, remote layout, protocol notes) saves locally to your browser — private to you.

I'll build this as one self-contained web app and publish it as a link (Web Bluetooth/Serial need a secure https context to work reliably, which a plain downloaded HTML file often can't guarantee).

Let me know if this matches what you're picturing, or if you'd rather trim scope (e.g. skip IR/USB for v1 and focus on BLE + the music-sync engine first) — then I'll build it.
